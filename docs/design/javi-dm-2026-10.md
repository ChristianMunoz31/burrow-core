# Javi DM-style helper and insight notifications (2026-10)

> Superseded 2026-11-05 by [ADR 0002](../adr/0002-free-for-everyone.md) for everything about Free and Pro: Burrow is free for everyone, so the Free-versus-Pro rules, gates, notices and upsell copy below are history. Every feature is on in an official build; a core-only build says "not included in this build".

> The other-workspace part of R16 is superseded 2026-10-10 (docs/design/nav-sections-2026-10.md): the count is every unread item except the current page's.
> R1 is superseded 2026-10-10 by the owner (see "Update 2026-10-10: the current-page notice" at the end): the page on screen counts while it has data and was not opened in Javi since it last changed, and own edits count.

**Implementation status:** design final pending owner decisions (section 8); implementation not started and merges after `feat/workspaces`.

Branch `feat/javi-dm` (base `main` 9ba27a5). Design only; coders implement it exactly. No commits by the designer. Revised after the design critique, the UX copy pass, the security and privacy review and the orchestrator rulings (see "Critique and copy", "Security and privacy review" and "Orchestrator decisions").

Owner request: "restructure Javi to look like a DM from a friend, bottom right of the pages, with new notifications on AI insights."

Summary:

- Javi already is a bottom-right round launcher plus a non-modal panel, and the Free "insight card" is just the Free mode of that panel. This design restyles the launcher, panel and messages into a direct-message look and adds a code-only notification layer. No new top-level widget.
- The launcher keeps its place and size and gains an unread count. The count covers the current workspace only and never the page you are on. The panel header reads like a DM header: sparkle avatar, "Javi" with a non-truncating "AI helper" tag, then "About {pageLabel}" and the existing source badge. Javi's messages sit left, the user's follow-ups right (Pro). The page insight is Javi's first message; a short greeting replaces the empty-state card.
- Notifications live in one `app_state` key, `javi.inbox`, that holds read markers only. Items are derived on read by code: a page whose data changed since its last insight, today's briefing (Pro), finished folder summaries. Edits you make on a page never flag that page or the pages that share its data; changes made from elsewhere (another device, a Javi change you approve on another page, an import from Settings) do (2.4). The client reports the page it is on in a JSON POST on every page change, and the server ignores writes to the tables behind that page. The inbox routes have their own rate limit and never spend Javi's AI limit. Zero new model runs by default.
- "New for you" is a compact strip outside the scrolling thread: one list of all rows in its own short scroll area (about three rows tall), no disclosure button. It lists exactly the items the count counts. Items of the other workspace are neither counted nor shown until the user switches workspace; they stay unread in `javi.inbox` (R16).
- The bell keeps code-computed "Today's alerts". AI-born items go to Javi's count. No item appears in both.
- The Home briefing card moves into the DM as Javi's first message on Home (owner decision 9, recommended). Home keeps one code-only button for Pro, "Open today's briefing in Javi".
- Bundle gate: total JS delta <= 0, CSS total <= 31.9 KB and initial JS <= 146 KB, measured on top of merged `feat/workspaces`. The base plan is estimated at about -150 B total JS using no owner-gated item other than the recommended decision 9 (briefing move); if decision 9 is declined, implementation stops and reports (6.1) (R16, margin target <= -150 B; the security fold added about +30 B, paid for by moving fallback cut F1 into the base plan as RC-6, R25). Owner-gated items (bell fold, pattern row) are optional, never required (6.1).

Alt+J does not collide with Ctrl+K, Alt+Left, Alt+1, Alt+2 or Alt+C. `e.code` keeps it layout independent and avoids the macOS Option+J character. No known conflict in Chromium, Edge or Firefox; NVDA and Narrator pass Alt chords; JAWS is checked by hand in WP-D.

Merge gate for Alt+J: verified in `npm run desktop:dev` on Windows x64 and arm64, no beep and no menu-bar activation on Alt release, tested together with the workspaces Alt+C. If it fails, Alt+J is dropped (fallback cut F3, 6.1). Ctrl+Shift+J is not a fallback (it opens DevTools).

### 1.8 Accessibility

- Region vs dialog: keep `role="dialog"` without `aria-modal`. It opens on demand from a button with `aria-haspopup="dialog"`, Escape closes it, focus moves into it and back. Keeping the role also keeps the e2e locators (`dialog "Javi"`).
- Launcher name: "Ask Javi about this page" when nothing is unread; "Ask Javi about this page, {n} new for you" otherwise, with the real number (the name is not capped at 9; only the visible count shows "9+"). Description "AI helper" (`aria-description`), shortcut `aria-keyshortcuts="Alt+J"`. The visible count is `aria-hidden`.
- Launcher `title`: dropped by RC-6 (R25). Accepted trade-off: mouse users lose the hover tooltip, while the accessible name, description, `aria-keyshortcuts`, the palette hint and the visible "AI helper" tag in the open DM stay. Add-back rule: restore the title ("Ask Javi, AI helper (Alt+J)") if the measured gate has 20 B or more headroom.
- Dialog description: `aria-describedby` reads "About {pageLabel}" and the source badge text.
- New-items announcer (in `JaviAdvisor`): one `<p role="status" className="sr-only">`, mounted empty while the launcher is shown. It speaks "Javi: {n} new for you" (n = the new count) only when the count rises above a value already known in this session, at most once per 2 s (the last rise wins), and clears the text after 5 s. Never on the first load, on a decrease, on a refetch with the same ids, while the panel is open, or while the launcher is hidden.

### 2.2 Inbox state (JSON contract)

`app_state` key `javi.inbox`. Read markers only, no content.

```json
{
  "v": 1,
  "createdAt": "2026-10-09T08:00:00.000Z",
  "pages": {
    "budget": { "seenAt": "2026-10-09T08:05:00.000Z", "changedAt": null },
    "todos": { "seenAt": "2026-10-08T19:00:00.000Z", "changedAt": "2026-10-09T07:40:00.000Z" }
  },
  "briefingSeenAt": "2026-10-08T07:12:00.000Z",
  "foldersSeenAt": null
}
```

Rules (server `normalizeInbox`, SP-9):

- The raw stored value is checked first: more than 4 KB of JSON, or not a plain object, is treated as missing.
- `v` must be `1`, else the value is treated as missing.
- `createdAt`: ISO string; it is the baseline for any marker that is null, so an upgrade never surfaces old briefings or summaries.
- `pages`: built on `Object.create(null)` by iterating the `INBOX_PAGES` allowlist (never the input's keys, so `__proto__` and other prototype names cannot enter); each value exactly `{ seenAt: ISO, changedAt: ISO | null }`; anything else dropped.
- `briefingSeenAt`, `foldersSeenAt`: ISO or null.
- Unknown keys dropped. Size is bounded (11 pages). A value that was normalized differently from what is stored is rewritten in canonical form at the next write (never by a GET).
- A missing or invalid value is a baseline in memory (`createdAt = now`) for reads. The row is written only by the read POST (the first one writes the baseline, SP-8), the advice route (`markPageSeen`, which also writes the baseline when missing), the write observer and the briefing refresh route (`markRead(['briefing'])`, SP-18). `GET /api/jarvis/inbox` never writes.
- Every read-modify-write of the row is synchronous: `selectOne` and `upsert` from `server/db/query.js` inside one `withTransaction`, with no `await` between them (SP-3). `server/javi/inbox.js` does not import `dataAccess.js`.
- The active page (2.4) is in memory only; it is never stored in this row, logged or audited (SP-16).

Persistence decisions:

- `AUTO_STATE_KEYS` gains `['javi.inbox', () => true]` (written without user data; same class as the dismissal flags).
- `PUT /api/state/javi.inbox` is refused (`403 protected_key`): the key has its own routes and one writer. Implement as `ROUTE_OWNED_STATE_KEYS = new Set(['javi.inbox', 'jarvis.briefing.latest'])` checked in `isStateRouteDeniedKey` (`jarvis.briefing.latest` added by SP-5, see 7.1). Neither key is added to `PROTECTED_APP_STATE_KEYS`, so restore keeps the backup's rows for them (F38).
- Local only (SP-14): new set `LOCAL_ONLY_APP_STATE_KEYS = new Set(['javi.inbox'])` in `server/dataBrowser/redact.js`, next to `HIDDEN_APP_STATE_KEYS`, which spreads it in. Because `EXPORT_SKIP_APP_STATE_KEYS` is that same set (F38), the export ZIP never carries the row; the importer (`importExport.js:249`) skips a `LOCAL_ONLY_APP_STATE_KEYS` key as `protected`, so an archive can neither restore old markers nor bring another computer's markers. Backups (VACUUM INTO) and restore keep it, so restored markers match the restored data. The direct-Burrow import copies the database file and keeps it too.
- Data browser and `GET /api/state`: hidden, through the same `HIDDEN_APP_STATE_KEYS` entry. This is cheap (one server-side set entry, no bundle bytes) and consistent with the set's rule ("rows no API ever returns"): only the inbox routes read the row, and they return derived items, not the row.
- A data reset removes it with the rest of `app_state`; the next read POST writes a new baseline.
- Backup fingerprint (SP-15, accepted): `contentFingerprint` (`server/backup/snapshot.js:157`) hashes `app_state`, so a day on which a marker changes makes that day's automatic backup count as changed. No fingerprint exception is added; at most one extra backup a day, which retention already bounds.

### 2.3 Item contract

Derived on every read, unread items only, sorted by `at` descending.

| Item | `id` | `kind` | `page` | `to` | `label` (fixed copy) | `workspace` | `at` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Page changed | `page:budget` | `page` | `budget` | `/budget` | `{Label} changed since your last insight` (e.g. "Budget changed since your last insight") | `budget` | `changedAt` |
| Briefing | `briefing` | `briefing` | `home` | `/` | `Today's briefing is ready` | null | `generatedAt` |
| Folders | `folders` | `folders` | null | `/folders?folder=${encodeURIComponent(latestId)}` when exactly one summary is new, else `/folders` | `A folder summary is ready` or `{n} folder summaries are ready` | null | latest `summary_at` |

A page item is unread when `changedAt !== null && changedAt > seenAt`. `{Label}` is the page label from `server/javi/pages.js`. Paths come from a server table `JAVI_PAGE_PATHS` in `server/javi/pages.js` (`budget-planner` is `/budget/planner`, `subscriptions` is `/budget/subscriptions`, `data-browser` is `/settings/data`, `home` is `/`, others `/<key>`); a parity test checks `resolveJaviPageKey(path) === key` for each. The folder route carries the folder's UUID only (SP-7, F40), never a name or path.

### 2.4 Change detection (the "fingerprint")

Code only, no hashing of page text, no polling of tables.

1. New neutral module `server/db/writeEvents.js` (imports nothing) with `onTableWrite(listener)` and `emitTableWrite(table, key, db)`. `query.js` calls `emitTableWrite` after a successful `insert`, `update` (only when the UPDATE statement ran and returned at least one row; the empty-patch branch at `query.js:262-265` runs a SELECT and never emits, SP-12), `upsert` and `remove` (when `changes > 0`). For `app_state` the `key` argument is `row.key` (insert, upsert) or null. `removeAll` (data reset only) does not emit. A listener that throws is ignored.
2. Commit-only delivery (SP-6): `writeEvents.js` keeps a buffer per database handle (`WeakMap`). `withTransaction` (`server/db/index.js:182`, F36) calls `openWriteBuffer(db)` before `BEGIN IMMEDIATE` at depth 0, `releaseWriteBuffer(db)` right after a successful `COMMIT` (delivers the buffered events in order, then drops the buffer) and `dropWriteBuffer(db)` on a depth-0 `ROLLBACK`. A nested savepoint takes `writeBufferMark(db)` at entry and calls `truncateWriteBuffer(db, mark)` on `ROLLBACK TO`. `emitTableWrite` appends to the open buffer of its handle, and delivers at once when that handle has no open buffer (an autocommit write outside any transaction is already committed). A dry-run import (`importParsed({ dryRun: true })`, `importExport.js:361-373`) therefore emits nothing, and neither does any other rolled-back transaction.
3. Active page (SP-8): the server learns the page on screen only from a JSON POST. The client sends `POST /api/jarvis/inbox/read` with `{ ids: [], active: pageKey }` on every page key change (and with its real `ids` when it marks something read), and uses the answer as the list. `GET /api/jarvis/inbox` has no `active` parameter and no side effect. `server/javi/inbox.js` keeps the page in one module variable through `setActivePage(key | null)`: null at start, last report wins (the desktop app has one window). A cross-site page cannot set it, because a cross-site form or image request cannot send `application/json` (the route answers `415` to anything else).
4. `installInboxWriteObserver()` (called once from `server.js` next to the route registration) installs one listener. It maps the table to pages with `TABLE_PAGES`, and `app_state` keys with the exact list `STATE_KEY_PAGES` (SP-12: the five budget data keys only, never the `budget:defaultView` or `budget:defaultMonth` preferences, F40). Every other table or key is ignored (including `javi.inbox` itself, so there is no loop). The decision is taken synchronously when the event is delivered (the write itself for an autocommit write, the `COMMIT` for a transaction, in the same tick, since transactions are synchronous): **if the active page is one of the write's mapped pages, the write is the user's own edit and is ignored entirely** (no page of that write is flagged; adding a transaction on Budget flags neither Budget nor Planner nor Subscriptions). Otherwise the mapped pages go into an in-memory pending set.
5. When the first page enters an empty pending set, the observer takes `captureDataGeneration()` (SP-11) and schedules one `setImmediate` flush; the flush coalesces the pending set (an import of thousands of rows is one flush).
6. The flush drops everything when that captured `isStale()` is true (data reset, restore, closed gate). Otherwise, in one synchronous `withTransaction`, it reads `javi.inbox`; for each pending page with a `seenAt` and with `changedAt === null || changedAt <= seenAt` (SP-4) it sets `changedAt = now`. It writes the row only if something flipped, so a page costs at most one extra `app_state` write per read cycle. Database errors are logged by code only (never the page key or the row) and dropped.
7. `onDataReset(() => { pending.clear(); activePage = null; })` is registered by `installInboxWriteObserver()` (SP-11), so a reset forgets the pending set and the active page.

```js
export const TABLE_PAGES = Object.freeze({
  transactions: ['budget', 'budget-planner', 'subscriptions'],
  todos: ['todos'],
  habits: ['habits'], habit_completions: ['habits'],
  focus_sessions: ['focus'], countdowns: ['countdowns'],
  calendar_events: ['calendar'], journal: ['journal'],
  notes: ['notes'], bookmarks: ['bookmarks'],
});
// SP-12: exact keys, no prefix match (F40).
const BUDGET_PAGES = ['budget', 'budget-planner'];
export const STATE_KEY_PAGES = Object.freeze({
  'budget:targets': BUDGET_PAGES, 'budget:payees': BUDGET_PAGES, 'budget:spent': BUDGET_PAGES,
  'budget:structure': BUDGET_PAGES, 'budget:defaults': BUDGET_PAGES,
});
```

`todo_columns` is not mapped (SP-12): the default columns are seeded during a GET, and a column rename is layout, not data. A test checks that every `TABLE_PAGES` key exists in `TABLES` (`server/db/tables.js`).

Accepted imprecision: a typo fix counts as a change; writes Javi made after an Approve on another page count (the user was not on that page); a Settings import or a data-browser edit flags the pages it touched; `stampLegacyOpenTodos` (`dataRoutes.js:104`) can flag Todos once, when an older database's open todos get their status during a GET made from another page (a one-time stamp; nothing flags without a `seenAt`). A write still in flight while the user navigates can be judged against the next page (rare; at worst one false or one missed count). In the web build with two tabs, and on a LAN or Docker install used from two devices, the last report wins (SP-16: same user, no cross-user data; the value is never logged or audited). After a server restart the active page is null until the next page change or read POST. If the page-change POST fails (429 or network), the server keeps the old active page, so the next edit may flag a page (QA-13). Rolled-back writes no longer flag (item 2).

### 2.5 Read rules

| Item | Marked read when |
| --- | --- |
| `page:<key>` | The DM is open on that page (on open, or on arriving there while open), via `POST /api/jarvis/inbox/read`: `seenAt = now, changedAt = null` (SP-4; a later write made elsewhere flags the page again, 2.4 item 6). Marker values (SP-5): `briefingSeenAt` and `foldersSeenAt` are set to `max(now, item.at)`, where `item.at` is the `at` of the item being marked (`generatedAt`, latest `summary_at`). Items with a future `at` are already excluded (2.1); the max is defence in depth, so a read can never leave a marker older than the item it marked.

Stale insight on open: if `page:<key>` was unread at the moment of opening, `autoAdvise` is on, and the page thread has no user message, the open requests a fresh insight (`requestAdvice(key, true)`, the existing `?fresh=1` path) even when an older insight is in memory. Because edits made on the page itself never flag it, this item only exists for changes made while the user was elsewhere. With a user message in the thread (Pro), nothing runs; the header "Get a new insight for this page" button stays the way to refresh.

Home: when a briefing generated today (local date) exists and the user has Pro `briefings`, opening the DM on Home does not auto-run page advice; the briefing is the first message, and Get insight in the greeting stays one click away. This removes a model run.

### 2.6 Count, list and polling

- `rows` = unread items with `item.page !== pageKey` and (`item.workspace === null` or `item.workspace === workspace`). `count = rows.length`. The strip renders exactly `rows`, every one as a button. A test asserts `count === rows.length` and that the strip renders `rows.length` buttons.
- Items of the other workspace are neither counted nor shown, not even as a number (R16). They are not lost: they stay unread in `javi.inbox` and appear in the count and the strip as soon as the user switches to that workspace. No `other` value exists in the hook.
- The current page's item is never counted or listed. It still drives the stale-on-open rule.
- `workspace` comes from `useWorkspace()` (F29); while `ready` is false it is treated as null, so only shared items count.
- Query key `['jarvis-inbox']`, `GET /api/jarvis/inbox` (no parameters, no side effect, SP-8), `staleTime` 60 s, refetch on window focus only when stale (React Query default), `retry: false`, no `refetchInterval` (R16: a change made while the user stays on one page shows at the next navigation, window focus or read). GET is a handful of indexed reads.
- Page change (SP-8, SP-2): an effect on `pageKey` sends `POST /api/jarvis/inbox/read` with `{ ids: [], active: pageKey }` through the same sender as `markRead`, and writes the answer into the cache with `setQueryData`. That resets the query's staleness, so a page change is one POST and never also a GET, and the window-focus GET runs at most once per `staleTime` (the client dedupe SP-2 asks for). The effect runs only when `pageKey` changes, so a re-render sends nothing. The only doubled call is at app start (the mount GET next to the first page POST).
- Rate limits (SP-1, SP-2): the inbox routes are skipped by the global `/api` limiter and by the AI `strictLimiter`, and have their own `inboxLimiter` (7.1), so navigating never spends the shared AI limit of 20 per 15 minutes or the data routes' 300.

## 4. Tone

Voice rules for every Javi string written in code (model output is unchanged; no `PROMPT_VERSION` bump):

1. Javi speaks in the first person, short and plain; the user is "you".
2. Friendly, not human: no feelings, no "friend", no typing indicator, no human name or face, no "while you were away".
3. One idea per message. No exclamation marks in fixed copy.
4. Never "chat", never "AI service" or "chatbot". "Conversation" and "ask follow-up questions" are fine.
5. Sentence case, no em or en dashes, the ellipsis character only for in-progress states.
6. Previews name the place, never the content.
7. "Insight" for page advice everywhere in fixed copy ("Get insight", "Get a new insight for this page").

Final strings: the string table under "Critique and copy", "UX copy", "String table" is the single source. Coders copy it exactly; tests assert it.

## 5. Privacy of previews

1. The count is a number only; its accessible name adds only "{n} new for you".
2. Rows show fixed labels naming a place (a page label, "briefing", "folder summary"). Never a folder name, file name, note or journal text, amount or model text. A Journal, Notes or Health row says only that the page changed.
3. Items of the other workspace are not shown at all, not even as a number: the Budget workspace never shows that a Journal page changed, and the reverse. They appear after the user switches workspace.
4. Model text (insights, briefing digest) appears only inside the open DM, as today. The Home button is fixed text.
5. Toasts: off. If turned on, same fixed labels, never `page:` items.
6. Budget-only text previews (a code-computed line such as a month-over-month change in a row): not built (owner decision 5, recommended off).
7. `javi.inbox` holds keys and timestamps only. It is behavioural metadata (when you looked at which page), so it never leaves the computer through an export, an import never sets it, and the data browser and `GET /api/state` hide it (SP-14, 2.2). Backups and restore keep it, since they never leave the computer. The active page is in memory only. A folder row's route carries the folder's UUID only (SP-7).
8. The inbox routes and the observer never call a model and never touch cloud; audit rows are not written for them, and the active page and page keys are never logged (SP-16).
9. Forged or imported timestamps cannot pin an item: a future or invalid briefing `generatedAt` or folder `summary_at` creates no item, imported folders waiting for confirmation never count, and `jarvis.briefing.latest` can no longer be written through `PUT /api/state` (SP-5, 7.1).
10. The briefing digest renders only through `JaviMessage` (via `TimelineMessage`), which drops images and uses `SafeLink`, never through the plain `Markdown` that `BriefingCard` used (SP-17, `JaviMessage.jsx:57`, `BriefingCard.jsx:140`).

## Update 2026-10-10: the current-page notice (supersedes R1)

Owner request: "also have javi always show notification if the page has populated data". Owner choice: the badge shows on any page that has data until the user opens Javi on that page, and comes back when that page's data changes (Budget with transactions: 1; open Javi on Budget: cleared; add a transaction: 1 again). This reverses R1, under which the active page was never counted and own edits on it were ignored at write time.

Rules as built:

- Page has data: a code-derived signal each page passes as the third argument of `usePageContext(key, builder, data)`, from data the page already loaded (no new request): falsy without records, else a value whose identity changes with the data. Only the Javi host reads it, through a second context in `PageContextContext.jsx`, so a change never re-renders the page tree. Per page: Budget and Budget Planner, real transactions (not the sample dashboard) or a saved target or payee (`hasBudget` in `javiBuilders/budget.js`, signal = the month plan); Subscriptions, at least one detected subscription or bill; Todos (any todo, not only the Work or Home filter), Habits, Focus (any session), Countdowns, Journal, Notes, Bookmarks, at least one record; Calendar & Weather, at least one event (weather alone does not count); Sleep & activity, at least one day of Oura data. Home, Settings, Browse your data and Folders have no current-page notice (Home keeps the briefing).
- Seen: the existing `javi.inbox` markers. A page with no marker was never seen. The write observer no longer skips writes made while their page is on screen (the server-side active page is gone), so every committed write to a page's data sets `changedAt` once `seenAt` exists. `health` joins `INBOX_PAGES`; it has no table, so it is unseen only until its first open. Stored rows keep the same shape (`normalizeInbox` unchanged); an old row without a page's marker means never seen.
- API: `GET /api/jarvis/inbox` and `POST /api/jarvis/inbox/read` both answer `{ data: { items, unseen } }`, where `unseen` lists the `INBOX_PAGES` keys with no marker or with `changedAt > seenAt`, in allowlist order. The read POST still accepts `active` (validated, then ignored) so an older open tab keeps working; the client no longer sends it. Reading `page:<key>` now writes a marker for a never-seen page too. Validation, no-store, the inbox limiter and the no-logging rule are unchanged.
- Client: `count = rows.length + (currentPageHasData && currentPageUnseen ? 1 : 0)`; `rows` (the New for you strip) still lists other pages only, since the current page's notice is the insight itself. The bar name stays "Javi, AI helper, {n} new for you" with n including the current page, and the announcer rules are unchanged. Opening Javi on a page sends the read POST for `page:<key>` when that page is listed or unseen (advice success still marks it server side). When the current page's data signal changes while the page counts as seen, the hook asks the inbox again after 1 s (the save may still be in flight; a burst is one request), so an own edit shows the count without a navigation.
- A change made while the window is open on that page shows the count after the window closes (the insight on screen was about the older data), and the next open asks for a fresh insight through the existing stale-on-open rule.
- Data reset, erase, import and backups: unchanged (erase empties the markers, so every page with data counts again).
- Review fixes (2026-10-11): `usePageContext` stores `false` for a registered page with no records and `null` only when no page is registered, so a lazy page registering one render after the route change is not a data change (no second read POST). The new-items status takes a new baseline on a page change and when the current page gains or loses data, so the current-page notice joining the count is never spoken; rises from the inbox are. The open read mark runs again once the first inbox answer lands. Focus return skips an opener that is disabled or inside `aria-hidden` (the Back placeholder on Home).
- Free and Pro both get it (insights are Free). Code only: no model call, no network, no migration.
