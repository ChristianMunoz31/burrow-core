# Weather location in the desktop app (2026-10-11)

## Problem

After #100 the weather shows only in the Javi card on Home. Its location came from `navigator.geolocation`, asked automatically as soon as Weather was on, with a fallback to the server's `WEATHER_LAT` / `WEATHER_LON` (which the desktop shell never passes to the sidecar). In the Tauri desktop app, and in particular the Microsoft Store (MSIX) package, the geolocation request can be refused or never answered, so a desktop user could see "Allow location access to see the weather here." with no place to allow it. `docs/MICROSOFT_STORE.md` also said the user could type a latitude and longitude, which no screen offered.

## Findings (time-boxed, about 15 minutes)

1. **wry 0.57 (our version, `src-tauri/Cargo.lock`) only answers WebView2 `PermissionRequested` when the app gives it a handler.** In [`src/webview2/mod.rs` at wry-v0.57.0](https://github.com/tauri-apps/wry/blob/wry-v0.57.0/src/webview2/mod.rs) the only built-in handler auto-allows `CLIPBOARD_READ` when clipboard is on. A second handler is added only if `attributes.permission_handler` is set; it maps `COREWEBVIEW2_PERMISSION_KIND_GEOLOCATION` to `PermissionKind::Geolocation` and calls the app's closure. `PermissionResponse::Default` "does nothing, let WebView2 show default prompt". The builder hook is `WebViewBuilder::with_permission_handler` ([`src/lib.rs`](https://github.com/tauri-apps/wry/blob/wry-v0.57.0/src/lib.rs)).
2. **Tauri v2 (2.12.1) has a hook, and Burrow does not use it.** `tauri-runtime-wry` passes `permission_request_handler` to wry's `with_permission_handler` ([`crates/tauri-runtime-wry/src/lib.rs`](https://github.com/tauri-apps/tauri/blob/tauri-runtime-wry-v2.12.1/crates/tauri-runtime-wry/src/lib.rs)). The public API is `WebviewBuilder::on_permission_request` and `Builder::on_permission_request` ([`crates/tauri/src/webview/mod.rs`](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.1/crates/tauri/src/webview/mod.rs), [`crates/tauri/src/app.rs`](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.1/crates/tauri/src/app.rs)); its docs say a saved allow or deny in the webview is used without calling the handler. `src-tauri/src/lib.rs` registers no handler, so a geolocation request in the desktop app falls to WebView2's own permission prompt, then to the Windows location setting.
3. **MSIX full-trust and the `location` device capability: not confirmed.** Our Store manifest (`scripts/release/storeManifest.mjs`) declares only `runFullTrust` (plus `unvirtualizedResources` in the appdata flavor) and no `<DeviceCapability Name="location"/>`. Microsoft's [UWP WebView docs](https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.controls.webview) say an app that uses location in a web view must declare the location capability and handle `PermissionRequested`; the [capability declarations page](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations) lists `location` as a device capability. We found no Microsoft page that says whether a packaged full-trust WebView2 app needs it, and we could not test on Windows from here. Treat geolocation in the Store package as possibly unavailable.

Conclusion: geolocation in the desktop app depends on a WebView2 prompt, the Windows location setting and, for the Store package, a capability we do not declare. It cannot be the only way to get a forecast.

## Decision

- **A typed location is the source of truth.** Settings > Network shows, in the Weather row and only while Weather is on, a Location form: Latitude, Longitude, Save, Use my location, and Clear when one is saved. Input is a plain decimal with up to 4 decimals (lat -90 to 90, lon -180 to 180), checked in the browser (`src/utils/weatherLocation.js`) and again on the server (`server/weatherLocation.js`). The server stores it rounded to 2 decimals (about 1 km) in `app_state` `weather.location` as `{ lat, lon }`.
- **Routes:** `GET`, `PUT` (body exactly `{ lat, lon }`; `400 invalid_location` with fixed copy) and `DELETE /api/settings/weather-location`, `no-store`, local only (no network call, so no `requireNetwork`).
- **Geolocation only on a click.** `useWeather` no longer calls `navigator.geolocation`. Use my location (Settings) asks once per click, fills the fields with rounded values and does not save; the user clicks Save. If it fails or is declined: "Burrow couldn't get this computer's location. Type your latitude and longitude instead, then click Save." With Weather off the form is not shown, so there is no prompt and no request.
- **Forecast order:** `GET /api/weather` (still behind `requireNetwork('weather')`) uses explicit `lat`/`lon` query values (API callers), then the saved location, then `WEATHER_LAT` / `WEATHER_LON`; with none it answers `503 { error: 'weather_location_missing', code, message }`. The Javi `get_weather` tool and the daily briefing use the same resolver (saved, then env). `fetchWeather` rounds every coordinate to 2 decimals before the request, so only rounded values leave the computer. The response carries `locationSource` (`query`, `saved`, `default`) for the Javi page context.
- **Cache:** the forecast URL has no coordinates, so `GET /api/weather` answers `no-store`: a browser HTTP cache could otherwise answer for a location that was since changed, cleared, erased or restored. React Query keeps the forecast for 30 minutes (`staleTime`), and Save or Clear resets the `['weather']` query, which drops the old forecast at once (so the Javi page context never reads the previous place) and refetches an open one. The response carries only `current`, `daily` and `locationSource`, never the coordinates or time zone Open-Meteo echoes back. Bad `lat`/`lon` query values answer `400 invalid_location` with the same fixed copy as the settings route.
- **Saved value not loaded:** if `GET /api/settings/weather-location` fails, the form says "Burrow couldn't load your saved location. Try again." with a Retry button, and the fields, Save and Use my location stay off until it loads, so a Save never overwrites a value the form never showed. A field error moves focus to the first invalid field, which carries `aria-invalid` and `aria-describedby`, styled with `formErrorClass`.
- **Home card:** with no location the weather slot is one muted line, the link "Set your location in Settings to see the weather." (`/settings#network`), instead of the dead end.
- **No shell change.** No permission handler, no new manifest capability, no new network feature or host. The `weather` policy text now says the coordinates are rounded, and that the forecast also loads for Javi's daily briefing while Weather is on (the briefing reads the forecast through the same resolver and `assertNetworkEnabled('weather')`).

## `weather.location` classification

It is user data, so it follows the ordinary rows: exported and imported (an imported value is validated again on every read and ignored if malformed), erased by Erase all my data (not in `KEPT_STATE_KEYS`), and restored with a backup (not protected). It is not in `PROTECTED_APP_STATE_KEYS` because importing a location cannot turn on a network call: the `network.optIn` row stays protected. It is in `ROUTE_OWNED_STATE_KEYS`, so `PUT /api/state/weather.location` answers 403 and the validating route is the only writer. Not hidden and not local-only. A direct-Burrow import treats it as user data (it is not in `AUTO_STATE_KEYS`).

## Follow-ups (not built)

- Test Use my location in the stable desktop app and in a sideloaded Store package on Windows. If WebView2 never prompts in the Store package, consider a `location` device capability (needs the owner, it changes the Store listing) or hiding Use my location in the Store build.
