# CLAUDE.md

Burrow is a local-first personal data OS (budget/transactions, todos, calendar, habits, journal, notes, bookmarks, countdowns, focus, health, weather, data browser, export/import) with a built-in AI assistant, Javi. Express API plus a React/Vite UI. Storage is a single SQLite file (`burrow.db`, `node:sqlite` `DatabaseSync`, WAL) in the data directory.

**Read `docs/PRODUCT.md` before planning any work.** It holds the mission (private, local-first budget and journal tracker for mainstream consumers), monetization (none: Burrow is free for everyone since 2026-11-05, with no paid tier, trial, license key, Buy button or upgrade prompt, see `docs/adr/0002-free-for-everyone.md`; the features that were Pro come from the private `pro/` module, which official builds include at no cost; the core source is public under AGPL-3.0-only at https://github.com/ChristianMunoz31/burrow-core (published 2026-11-04) while this repo stays the private working repo and the module stays private in `pro/` from the private repo `burrow-pro`, so copy may say the core is open source and AGPL, never that the private module is open source or that its source is public, and never offer Docker self-hosting, see `docs/OPEN_CORE.md` and `docs/PUBLISHING_CORE.md`), delivery (Tauri desktop for consumers, Docker internal), the rules below that are product requirements, and open decisions you must not resolve on your own. For any new or changed UI also read `docs/DESIGN.md` (tokens, shared components, copy rules, empty-state and error patterns); `/ship-feature` has a mandatory Design step for it. Hard product rules:
- AI summarizes, code calculates: compute every number natively in SQL/JS and pass only results to the model; never ask a model to do math.
- Never paywall the user's data; export, import, backups and privacy controls stay free.
- Automatic daily local backups with restore are a core requirement.
- Target ordinary CPU-only hardware; small models by default, graceful slow-inference handling.
- $0 marginal cost to the developer: no new hosted services, per-user APIs or store fees without owner approval.

## Principles

- Local-first. No cloud, no telemetry, no accounts. Data stays in open formats (SQLite, JSON, CSV, Markdown).
- Never add an outbound call without a network feature. The registry `NETWORK_FEATURES` lives in `server/netFeatures.js` (plain data, re-exported by `server/netPolicy.js`): add the id, hosts and a `policy` field (`sent`, `when`), then `requireNetwork(id)` on the route or `assertNetworkEnabled(id)` in library code, and run `npm run privacy:render` to regenerate `pages/` (`npm run check:privacy`, part of `npm run check`, fails while `pages/` is out of step with the registry). Current features: weather (location typed in Settings > Network or filled by a Use my location click, never an automatic geolocation request; stored rounded to 2 decimals in `app_state` `weather.location` by `server/weatherLocation.js` and `GET/PUT/DELETE /api/settings/weather-location` (`400 invalid_location`), the only writer (`ROUTE_OWNED_STATE_KEYS`); user data: exported, imported, erased; `/api/weather`, the Javi tool and the briefing use query coords, then the saved location, then `WEATHER_LAT`/`WEATHER_LON`, else `503 weather_location_missing`; `/api/weather` is `no-store`, returns only `{ current, daily, locationSource }` and answers bad query coords with `400 invalid_location`; `fetchWeather` sends only rounded coordinates; docs/design/weather-location-2026-10.md), oura (also covers testing a saved Oura token), sheets, cloudAi, aiLan, updates (GitHub release check that shows what's new, run from Settings > Updates, plus click-to-install in the stable desktop app and a manual installer download with its SHA-256 where the shell cannot install; hosts `github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`, and `api.github.com` for the releases-API check; Burrow Dev and the Store build make no request; Check now turns the feature on). There is no store or license feature (ADR 0002 removed `license`).
- Model downloads are the one documented exception to netPolicy: `POST /api/settings/ai/pull` only talks to a loopback Ollama, runs only on a user click whose label says Ollama downloads the model from the Ollama library, and Burrow itself makes no outbound call. Do not add any background or automatic pull.
- `mailto:` links (Help > Report content, the Report link under Javi replies; policy 11.16) hand a draft to the default mail app and send nothing from Burrow, so they need no netPolicy feature. The report draft never contains message text or other user data (`src/components/javi/reportContent.js`).
- In-app update install is the second click-only download, and it is not a server call: the server only saves a backup and writes one authenticated request line to the desktop shell, and the Burrow app (Burrow.exe) downloads and verifies the installer. It runs only on a click on Download and install, only when `updates` is on, only in the stable desktop app. Do not add any background, startup or automatic check, download or install, and no auto-install option.
- Never call a cloud LLM by default. AI runs on local Ollama (loopback only). A non-loopback Ollama host needs the `aiLan` opt-in; the OpenAI-compatible cloud endpoint (bring your own key, free core) needs `cloudAi`, a current two-checkbox consent for that exact base URL (`app_state` `ai.cloudConsent`, version 1; any base URL change clears it; `ai.cloud*` and `ai.settings` provider/cloud are never writable through `PUT /api/state` or import), a public https base URL (`validateCloudBaseUrl`; loopback and private ranges belong to `aiLan`) plus a saved key and model. Burrow never turns cloud on by itself. A broken cloud setup falls back to local, never the reverse.
- Cloud data categories (`server/ai/privacy.js`, `app_state` `ai.cloudCategories`; journal, notes, health and folders off by default) are enforced server-side: every model call passes a `scope` and `enforceCloudScope()` runs first in the client's `events()` (missing scope or a withheld category throws `CloudScopeError` before the transport). Features also filter first (page advice `applyPagePolicy`, Jarvis `policy.toolDecision`, briefing `filterBriefingSnapshot`, cross insights). Javi memory never goes to cloud; the scheduled briefing is local only. Under cloud, earlier assistant and tool rows (Jarvis history and advice threads) are never sent, only the user's own earlier messages, because local replies may quote withheld data. Withheld notices are fixed copy from `withheldMessage()`. Audit rows record `ai_kind`, `ai_host` and category names only. `aiBoundary.test.js` requires every AI consumer to be allowlisted with cloud test coverage.
- AI module boundary: all AI goes through `server/ai/index.js`. `isAiEnabled()` (`BURROW_AI !== '0'`) is the single licence seam. Get a client with `getAiClient({ purpose: 'chat' | 'tools' })`; routes use the `requireAi(purpose)` middleware, which answers before any SSE headers. No provider imports (`server/ai/providers/*`, `llmClient`, `llmErrors`) outside `server/ai/`, enforced by `server/__tests__/aiBoundary.test.js`.
- All DB access goes through `server/db/query.js` (re-exported by `server/db/index.js`) with allowlisted table and column identifiers from `server/db/tables.js`. No string-built SQL from request input.
- No personal data in the repo, fixtures, prompts or tests. No references to prior products or hosted deployments.

## Architecture

- `server.js` - Express app. Order matters: host guard (421), CORS, rate limits, auth gate (`APP_PASSWORD` + `AUTH_SECRET`, cookie `burrow_session`), secrets primer, routes, static UI, error handler. Exports `app` for supertest (no socket under `VITEST`).
- `server/config.js` - host/port/origins/trust-proxy/scheduler resolvers and `checkStartupSecurity` (non-loopback bind needs `APP_PASSWORD` + `AUTH_SECRET` unless `BURROW_ALLOW_INSECURE_LAN=1`; `AUTH_SECRET` >= 32 chars).
- `server/hostGuard.js` - Host allowlist (loopback always; others via `BURROW_ALLOWED_HOSTS` or the non-loopback bind host).
- `server/paths.js` - data dir, the one place that resolves it (`BURROW_DATA_DIR`, else `%USERPROFILE%\Burrow Data` for the Store build with the `userprofile` data location on the stable channel on Windows (`usesUserProfileDir`), else the per-OS default). `stableDefaultDataDirs()` lists every default folder of the stable Burrow (`%APPDATA%\Burrow` and, on Windows, `%USERPROFILE%\Burrow Data`). `server/dataLocation.js` is the compile-time marker (`appdata` default | `userprofile`, valid only with the Store distribution on the stable channel; startup exits 1 otherwise, before any data access); the Rust side is `src-tauri/build.rs` + `channel.rs` `DataLocation` + `exit_dialog.rs` `platform_data_dir`. `server/dataFolderOwnership.js` is the ownership rule of that folder (`.burrow-data.json` marker `{ app: 'Burrow', edition: 'store', dataLocation: 'userprofile', createdAt, formatVersion: 1 }`; `ensureDataDirOwnership()` runs at the top of `startServer`, before the desktop handshake, the import recovery, the restore journal, the database, the key file, and inside `getDataDir()` before any mkdir): a missing folder is created with the marker, a marked one is used, an empty one is adopted, and any other (unmarked and non-empty including hidden entries, corrupt marker, a file, a symbolic link or junction, any other reparse point such as a cloud-files placeholder) is refused, never written to, with exit code 5 (a folder that is missing and cannot be created, e.g. no parent, is the same exit code with its own message; the folder is created with one non-recursive mkdir, so the marker is only ever written into a folder the guard just created or saw empty; the marker rule is pinned for the server, the shell and `scripts/store/sideload-test.ps1` by `server/__tests__/fixtures/markers.json`); the Rust shell applies the same rule first in `src-tauri/src/data_guard.rs`, before it creates `<data folder>\logs`; no rule for appdata, direct or Dev. `server/dataFolderHealth.js` warns once (log line, `GET /api/app/info` `dataFolderWarning`, a dismissible card in Settings > Data & storage and on Home) when the data folder lies under a OneDrive root (env `OneDrive`, `OneDriveConsumer`, `OneDriveCommercial`) or is a linked folder; it never blocks.
- `server/channelGuards.js`, `server/pathGuard.js` - Dev channel isolation, run first in `startServer` (exit 1, no data-dir access): a Dev server refuses a data dir that equals, contains or lies inside a stable default (`%APPDATA%\Burrow`, and `%USERPROFILE%\Burrow Data` on Windows) or `BURROW_STABLE_DATA_DIR` (real paths, case-folded on Windows and macOS), and in desktop mode `BURROW_SHELL_CHANNEL` must equal the server's channel. Safety nets for mistakes, not a trust boundary (unbundled servers read `BURROW_CHANNEL` from the env).
- `server/db/` - `index.js` (handle, `withTransaction`), `migrate.js` + `migrations/NNN_name.sql` (forward-only, `schema_version`, pre-migration `.bak`), `query.js`, `stmtCache.js` (per-handle prepared-statement cache used by `query.js` and `pingDb`; only for all()/get()/run(), never iterate(); cleared on close via `clearStmtCache`), `tables.js`, `codec.js`, `errors.js`. `server/dataAccess.js` is the shared data API for routes, search and Javi tools.
- `server/netFeatures.js` - the outbound-network feature registry as plain data (id, label, description, hosts, `policy`); also the source of the published privacy page (`npm run privacy:render`). `server/netPolicy.js` - outbound opt-ins; state in `app_state` key `network.optIn`; env default `BURROW_NETWORK_OPTIN`.
- `server/updateCheck.js` - `checkForUpdate({ source })` (stable) has two sources of the PUBLIC repo `ChristianMunoz31/burrow-releases` (`UPDATE_REPO`; `publishPublic.js` gives it the same `vX.Y.Z` tags as the private source repo, so the comparison against the app version is unchanged; an installed app cannot read the private repo anonymously). `source: 'manifest'` (copies whose shell can install, `canInstall`) fetches `latest.json` (`LATEST_MANIFEST_URL`, `https://github.com/ChristianMunoz31/burrow-releases/releases/latest/download/latest.json`); `source: 'release'` (every other stable copy, chosen by the settings route from `installSupported()`) reads GitHub's public API `RELEASE_API_URL` (`https://api.github.com/repos/ChristianMunoz31/burrow-releases/releases/latest`, one request, no redirects, 256 KiB) and `parseLatestRelease()` accepts only a published (not draft, not prerelease) release with a strict `vX.Y.Z` tag, a valid `published_at` and both installers plus `SHA256SUMS.txt` among its asset names (asset URLs in the response are ignored); `releaseNotesText()` keeps only the lines under a `## What's new` heading as plain text. `fetchPinnedText()` is the shared fetch: at most 3 redirects done by itself (`redirect: 'manual'`, https only, default port only, no userinfo, hosts `UPDATE_REDIRECT_HOSTS` = `github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`, the same list as the shell's `redirect_allowed` and netPolicy) with a byte cap. `fetchLatestManifest()` caps the body at 64 KiB and validates the manifest: strict stable `x.y.z` (`STABLE_VERSION_RE`, at most 9 digits per part, the same cap as the shell), `pub_date`, both platforms with a non-empty signature (at most 4096 chars) and the exact pinned installer URL `.../releases/download/v{version}/Burrow-Setup-{x64|arm64}.exe` (`installerUrl`). The `notes` field is forwarded sanitized (CRLF to LF, C0 and C1 controls, zero-width and bidi marks, the word joiner and the BOM removed, at most 2000 chars, else null). `fetchInstallerChecksum({ version, arch })` fetches only the pinned `sumsUrl(version)` (`SHA256SUMS.txt`, at most 4 KiB), writes ONE audit row (`github.com`) and returns the lowercase SHA-256 from `parseSums()` (exactly one matching line, else a failure); it throws while `updates` is off and makes no request for a bad version or architecture. There is no license rule on updates (ADR 0002): any version installs and runs fully. The Burrow Dev query (`queryDev`, private repo through `api.github.com`) is no longer reachable from the routes. `checkForUpdate` never throws upstream: returns `current | available | unavailable`, cached 6 h / 15 min per `channel:source:version`; results carry `source` and `available` adds `notes`. Audit host: `github.com` (manifest source, checksum), `api.github.com` (release source, Dev). Route `GET /api/settings/updates/check` answers `store_managed` (Store build) and `dev_managed` (Burrow Dev) before the opt-in and without any request, and adds to `available` results per request, never cached: `canInstall` (`isShellUpdaterAvailable()` in `server/desktop/shellChannel.js`: desktop mode, stable channel and `BURROW_SHELL_UPDATER=1`), `canDownload` (`isManualDownloadAvailable()`: the stable direct desktop app on Windows x64 or arm64 without a working shell updater, i.e. the placeholder key). The check itself never downloads anything.
- `server/updateInstallRoutes.js` - `POST /api/settings/updates/install` (body exactly `{ version }`, strict `x.y.z`), the click-to-install handoff. Order: `requireNetwork('updates')`, JSON type, limiter (5 per 15 min), body check, capability check, a data-lock check (a running backup or erase, or a closed request gate: `409 backup_busy`; a restore: `503 db_restoring`), single-flight lease (held for 16 min after a handoff, which covers the shell's 15 min download timeout; released at once on failure and when the server stops via `releaseUpdateInstallLease()`), a fresh `checkForUpdate({ refresh: true })` whose `latest` must equal the clicked version, `createBackup({ kind: 'manual', skipIfUnchanged: false })` (a failed backup stops the update), then `requestShellUpdate(version)`, then one audit row `recordNetworkCall('updates', 'https://github.com', 'ok', { result: 'started', by: 'app' })` (stored as `meta.net_result` and `meta.net_by`; network activity shows "Update download (Burrow app)" with result `started`). Success `202 { data: { status: 'handed_off', version, backupId } }`. The route downloads and installs nothing. `registerUpdateInstallRoute(app, deps)` injects every step for tests. `registerManualDownloadRoute(app, deps)` adds `POST /api/settings/updates/manual` (body exactly `{ version }`, own limiter of 5 per 15 min, `requireNetwork('updates')`) for a copy without a working shell updater: JSON type, body check, `409 update_manual_unsupported` (unless `isManualDownloadAvailable()` and a usable architecture), single flight (`update_in_progress`), the data-lock check, a fresh `checkForUpdate({ refresh: true, source: 'release' })` whose `latest` must equal the version (strictly newer only: no downgrade), `fetchInstallerChecksum` (`503 update_checksum_unavailable`), then `createBackup` (a repeat click for the same version within 10 minutes reuses the backup id kept in memory per process and skips it; the checksum runs on every click). Success `200 { data: { status: 'ready', version, arch, fileName, installerUrl, sha256, sumsUrl, backupId } }` where both URLs are built by the server from the version (`installerUrl()`, `sumsUrl()`); the route downloads no installer and never returns a URL taken from a network response. The UI (`UpdatesSection`) shows the expected SHA-256 and the `Get-FileHash` command and the browser downloads the pinned URL.

## Conventions

- Error contracts: gated-off network feature returns `403 { error: 'network_opt_in_required', feature, message }`; a module route in a build without the private module returns `501 { error: 'pro_not_included', code: 'pro_not_included', feature, message }` (`no-store`, fixed copy `MSG_PRO_NOT_INCLUDED` "This build of Burrow does not include this feature. The official Burrow app includes it at no cost.", mirrored by `PRO_NOT_INCLUDED_COPY` in `src/constants/proFeatures.js`; client `isProNotIncludedError(err)`; there is no `403 pro_required` any more); AI that cannot run returns `503 { error: 'ai_not_configured' | 'ollama_unavailable' | 'ai_warming_up', reason, message }` (`ai_warming_up`, reason `ai_warming_up`, is a busy local (loopback) Ollama whose quick health probe timed out with nothing known from a probe in the last 10 minutes and no answer within the patient re-probe, one overall deadline of `BURROW_AI_WARMUP_PROBE_MS` (default 30 s) for version, tags and show together, shared by every request waiting on that host and abandoned by a request that closes; it is never reported as `ollama_unavailable` for a loopback host, which stays for a refused connection; a non-loopback (`aiLan`) host that times out is `ollama_unavailable`; a first-token timeout or connection error on a local call, and any host setting change, drop the remembered probe; status checks never wait for it) a full queue returns `429 { error: 'ai_busy', message }` and a second `POST /api/jarvis` for a conversation that already has a run returns `409 { error: 'conversation_busy', code, message }`, all sent before opening any SSE stream; a cloud call whose setup changed while it waited in the queue (cloud turned off, or base URL, host or model changed) is refused right before sending with `403`/SSE `error` code `cloud_disabled` (`CloudScopeError('cloud_disabled')`, fixed copy "Cloud AI was turned off, so nothing was sent. Try again to use the AI on this computer.", nothing sent, not counted as a call or as shared categories; a rotated key on the same URL uses the fresh key); wrong Host returns `421`; `/api/oura` with no saved token returns `503 { error: 'not_configured', message }` (never sample data); an unmatched `/api/*` path returns `404 { error: 'not_found' }`; a non-string `q` on `GET /api/search` returns `400 { error: 'invalid_query', message }`; a malformed percent-escape in a route param returns `400 { error: 'invalid_request', message }`. Model pull: `400 invalid_model` (name not in `PULLABLE_MODELS`), `409 pull_in_progress`, `409 pull_requires_local_ollama` (host is not loopback), `503` as for other AI routes, all sent before any SSE headers; once streaming, events are `progress` (`phase`, `completed`, `total`), `done` (`{ model }`) and `error` (`{ code: 'pull_failed' | 'timeout', message }`), with fixed copy and no upstream text. - Streamed model output goes through `createStreamSanitizer()`; non-streamed output through `sanitizeModelText()`. Never echo provider error text to the client (use `classifyAiError`).

- Conventional commits (`feat(scope): ...`), branches `feat/`, `fix/`, `chore/`, `docs/`.
- Explain root cause before fixing a bug. Do not add features beyond the task.

## Windows notes

PowerShell 5.1 is the default shell: chain with `;` not `&&`, use `$env:VAR` not `$VAR`. Use absolute paths in tool calls; the working directory resets between shell calls.

In bash (Git Bash), discard output with `/dev/null`, never `nul`: bash writes a real file named `nul` into the working directory. In PowerShell use `$null` (e.g. `2>$null`). Quote paths that contain spaces.
